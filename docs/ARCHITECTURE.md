# معماری ثبت‌یار

این سند اصول طراحی و نقاط توسعه‌پذیری پروژه را توضیح می‌دهد.

## اهداف طراحی

1. **سادگی و سرعت برای کاربر** — کمترین کلیک، بیشترین سرعت در صدور فاکتور.
2. **ماژولار بودن** — هر بخش تجاری مستقل، قابل تست و قابل تعویض.
3. **استقلال از سرویس خارجی** — قابل اجرا روی هاست ایرانی، بدون وابستگی اجباری.
4. **موتور صوتی جدا و امن** — تشخیص صوتی هرگز مستقیماً عملیات مالی را اجرا نمی‌کند.

## لایه‌ها

### ۱) دیتابیس (`server/db`)
- SQLite تک‌فایل با WAL. اسکیمای کامل در `schema.sql`.
- قیمت‌ها بر حسب **ریال صحیح** ذخیره می‌شوند تا خطای اعشار پیش نیاید.
- **منبع حقیقت موجودی** جدول `inventory_transactions` است؛ هر تغییر موجودی یک
  تراکنش ثبت می‌کند و ستون `products.stock` همیشه با آن هم‌خوان می‌ماند
  (`server/modules/inventory/service.js`).
- تعویض موتور دیتابیس: چون همهٔ کوئری‌ها از لایهٔ ماژول‌ها عبور می‌کنند، مهاجرت
  به MySQL/Postgres با بازنویسی همین لایه (نه کل اپ) ممکن است.

### ۲) ماژول‌های تجاری (`server/modules/*`)
هر ماژول یک Router اکسپرس مستقل است که در `server/index.js` ثبت می‌شود. منطق سنگین
(مثل ساخت فاکتور) در فایل `service.js` جدا از لایهٔ HTTP قرار دارد تا هم از API و هم
از موتور صوتی قابل استفاده باشد.

### ۳) احراز هویت و دسترسی (`server/middleware/auth.js`)
نشست مبتنی بر کوکی + جدول `sessions`. سه نقش: مدیر، فروشنده، انباردار. `requireRole`
دسترسی هر Endpoint را کنترل می‌کند. همهٔ عملیات مهم در `audit_logs` ثبت می‌شوند.

### ۴) موتور صوتی (`server/voice/*`)
کاملاً مستقل و بدون وابستگی به دیتابیس (وابستگی‌ها به‌صورت تزریقی به `VoiceEngine`
داده می‌شوند). مسیر پردازش:

```
normalizer → intent → entities(+numbers) → matcher → validation
          → questions(ابهام) → confirmation → action(ماژول تجاری) → db
```

- **normalizer.js:** یکدست‌سازی حروف (ی/ي، ک/ك)، اعراب، فاصله‌ها و ارقام.
- **numbers.js:** تبدیل اعداد حرفی/رقمی و واحد پول («پنجاه هزار»، «۵۰ تومن»، …).
- **intent.js:** تشخیص دستور با قواعد کلیدواژه‌ایِ وزن‌دار و قابل‌گسترش.
- **entities.js:** استخراج اقلام، تعداد، قیمت‌ها، مشتری، تخفیف.
- **matcher.js:** جستجوی هوشمند (نه فقط تطبیق دقیق) با امتیازدهی؛ در صورت نزدیک‌بودن
  چند نتیجه، وضعیت `ambiguous` برمی‌گرداند تا از کاربر پرسیده شود.
- **recognizers.js:** رجیستری موتورهای تبدیل صدا-به-متن پشت یک Interface یکسان.

**نقطهٔ تعویض موتور STT:** پیش‌فرض `web` است (Web Speech API در مرورگر). برای موتور
سمت‌سرور کافی است پیاده‌سازی جدیدی با متد `transcribe(audioBuffer)` در `recognizers.js`
ثبت و `VOICE_RECOGNIZER` را در `.env` تغییر دهید؛ بدنهٔ اپ بدون تغییر می‌ماند.

### ۵) فرانت‌اند (`public/*`)
SPA سبک با Vanilla JS و **بدون build-step** تا روی هر هاستی به‌سادگی سرو شود.
- `app.js`: روتر hash، پوستهٔ اصلی، مدیریت تم، و **دستیار صوتی مرکزی** که کل مسیر
  امن (تفسیر → پرسش → تأیید → اجرا) را در UI پیاده می‌کند.
- `voice.js`: نیمهٔ مرورگری موتور صوتی؛ Web Speech API پشت یک Interface ساده.
- `format.js`: اعداد فارسی، تومان، و تبدیل تاریخ میلادی به **شمسی** (بدون کتابخانه).
- `pages/*`: هر صفحه یک ماژول مستقل که در `window.Pages` ثبت می‌شود.

## امنیت عملیات مالی (اصل کلیدی)

تشخیص صوتی نامطمئن نباید موجب ثبت/حذف داده شود. بنابراین:
1. سرور فقط «تفسیر» را برمی‌گرداند (`/api/voice/interpret`) و چیزی ذخیره نمی‌کند.
2. اگر ابهام یا اطلاعات ناقص باشد، پرسش تولید می‌شود.
3. نتیجه به کاربر نمایش داده و **تأیید صریح** گرفته می‌شود.
4. تنها پس از تأیید، APIهای تجاری (که خودشان اعتبارسنجی مستقل دارند) اجرا می‌شوند.

## افزودن قابلیت جدید (نمونه)

برای افزودن ماژول «هزینه‌ها»:
1. جدول `expenses` از قبل در `schema.sql` هست (نمونهٔ آماده).
2. پوشهٔ `server/modules/expenses/routes.js` را بسازید و Router بنویسید.
3. در `server/index.js` با `app.use('/api/expenses', require('./modules/expenses/routes'))` ثبت کنید.
4. در صورت نیاز صفحه‌ای در `public/js/pages/` اضافه و در `NAV` (فایل `app.js`) لینک کنید.

هیچ بخشی از اپ نیازمند بازنویسی نیست.
